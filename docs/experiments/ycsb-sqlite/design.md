# YCSB 동등 조건 측정: 실험 계획

| 항목 | 값 |
|---|---|
| 추적 | [YCSB 동등 조건 측정 #226](https://github.com/woonyong-choi/totedb/issues/226) |
| 관련 설계 | [아키텍처](../../architecture.md) |
| 사전 데이터 | 없음. 공개 C API·SQL 구현과 공식 YCSB 소스를 조사했으며 성능 데이터는 생성하지 않았다. |

## 목적

공식 YCSB의 같은 클라이언트와 워크로드로 ToteDB와 SQLite의 처리량·지연·실패를 비교한다. 비교 대상은 Java 바인딩과 JNI를 포함한 embedded SQL 호출 경로다.

## 가설

| 가설 | 예측 | 적용 범위 |
|---|---|---|
| H1 | 양쪽의 정식 실행 240회 모두 논리 연산 1,000회를 완료하고 오류와 재개방 검사 실패가 0건이다. | 아래 크기·동시성·A~F 조건 |
| H2 | E에서 ToteDB/SQLite 처리량 비율은 0.8보다 작다. | 크기 2개와 동시성 2개의 각 조건 |

H2는 TEXT 구간 조회에서 ToteDB가 전체 순회·정렬 후 LIMIT를 적용하고 SQLite가 기본 키 색인으로 순회한다는 소스 조사에 따른 예측이다. 성능을 미리 관측한 결론이 아니다. 다른 워크로드는 방향을 예측하지 않고 기술 통계로 보고한다.

## 비교 조건

| 항목 | 값 |
|---|---|
| 기준 조건 | SQLite `DELETE` journal, `synchronous=FULL`, `fullfsync=OFF` |
| 비교 조건 | ToteDB 공개 C API의 DURABLE 자동 commit, COW와 fsync |
| 실행 순서 | 크기 1,000·10,000행, A~F, 스레드 1·4 순. 조건별 반복 1·3·5는 ToteDB 다음 SQLite, 2·4는 SQLite 다음 ToteDB |
| 평가 방식 | 자동 수집·검사·집계. 사람이 결과에 점수를 매기지 않으므로 맹검 해당 없음 |

양쪽 모두 같은 `site.ycsb.DB` 구현, SQL 생성, 매개변수 변환과 결과 소비를 거친다. JNI 아래에서 각각 `tote_exec`와 `sqlite3_prepare_v2/bind/step/finalize`를 호출한다. SQLite 준비 문장을 재사용하지 않는다. ToteDB 공개 API에도 준비 문장 handle이 없기 때문이다.

스레드마다 native 연결을 하나 연다. SQLite 내장 busy 대기는 끄고 양쪽에 같은 재시도 정책을 적용한다. 확실히 적용되지 않은 BUSY만 최대 60초 동안 0.5ms부터 20ms까지 지수 대기한다. 재시도 시간은 연산 지연에 포함한다. 횟수와 예산 소진을 기록한다. 불확실한 commit이나 I/O 실패는 재시도하지 않는다.

키는 공식 YCSB 문자열을 그대로 TEXT 기본 키에 저장한다. 10개 필드는 각각 100바이트 BLOB이다. 선택 필드 조회와 부분 갱신을 보존한다. scan은 시작 키 이상을 문자열 오름차순으로 반환한다. F의 read와 update는 공식 클라이언트가 호출하는 별도 자동 commit이다.

## 측정 지표

| 지표 | 종류 | 정의 | 단위 |
|---|---|---|---|
| 크기·스레드·워크로드·엔진 | 조건 값 | 초기 행 수, YCSB worker 수, 공식 A~F, native backend | 행·개 |
| 처리량 | 측정 값 | 공식 `[OVERALL] Throughput(ops/sec)` | ops/s |
| 지연 p50·p95·p99 | 측정 값 | 공식 연산별 histogram percentile. 논리 연산과 F의 하위 read/update를 구분 | µs |
| 완료·반환 상태·재시도 | 측정 값 | 공식 연산 수와 status별 횟수, 바인딩 BUSY 횟수·소진 | 건 |
| 실행 시간·종료 상태 | 측정 값 | 공식 runtime, 외부 wall time, exit와 timeout | ms·s·코드 |
| 저장 결과 | 측정 값 | 닫은 뒤 재개방한 행 수·필드 수·값 길이·정규화 SHA-256, 갱신 차이 | 행·바이트·해시 |
| 반복 중앙값과 범위 | 계산 값 | 같은 조건의 성공한 다섯 반복에서 중앙값·최소·최대. 실패 수 별도 표시 | 원래 단위 |
| 대응 처리량 비율 | 계산 값 | 반복별 ToteDB 처리량/SQLite 처리량의 중앙값 | 비율 |
| 신뢰구간 | 계산 값 | 대응 비율 중앙값의 bootstrap percentile 구간 | 비율 |

공식 처리량의 runtime은 worker 시작부터 join까지이며 연결 초기화와 종료를 포함한다. 연산별 지연은 각 DB 메서드 호출을 잰 값이다. JVM 시작을 포함한 외부 wall time은 별도 지표다.

### 조건별 값

| 설정 | ToteDB | SQLite |
|---|---|---|
| 저장 API | `tote_open/exec/free/close` | `sqlite3_open_v2/prepare_v2/bind/step/finalize/close` |
| 내구성 설정 | 공개 API DURABLE, COW/fsync | `DELETE`, `FULL`, `fullfsync=OFF` |
| 내부 결과 처리 | 공개 API 결과 wire를 검사·해석 | sqlite3 결과를 직접 소비 |
| 페이지 크기 | 8,192바이트 | 생성 전 `page_size=8192`, 실제 값 조회 |
| 페이지 cache | 공개 API의 기본 256페이지 | 연결마다 `cache_size=256`, 실제 값 조회 |
| 파일 읽기 | 기존 `pread` 경로 | `mmap_size=0`, 실제 값 조회 |
| 고유 비용 | 공개 API의 전체 결과 직렬화 포함 | 호출마다 prepare/finalize 포함 |

내구성 설정은 정상 commit의 동기화 의도를 맞춘 조건이다. 전원 장애 보장이 같다고 가정하지 않는다. SQLite WAL이나 준비 문장 재사용을 튜닝한 최상의 성능을 뜻하지 않는다.

페이지 cache는 연결당 명목상 2MiB로 맞춘다. 캐시에 담는 페이지 종류와 메타데이터 비용이 달라 실제 메모리 사용량이 같다는 뜻은 아니다. 이 값은 ToteDB의 `PAGE_FILE_CACHE_PAGES=256`과 페이지 크기에서 정한다.

## 표본

| 항목 | 값 |
|---|---|
| 출처 | 공식 YCSB CoreWorkload의 합성 데이터와 A~F 요청 분포 |
| 크기 | 2크기×6워크로드×2동시성×2엔진×5반복 = 정식 240회 |
| 크기 근거 | 수집 한도. 로컬 두 크기에서 각 엔진·조건을 최소 다섯 번 교대 측정. 검정력에 따른 표본 산정에 해당하지 않는다. |
| 중단 규칙 | 각 child 180초. 실패·timeout을 보존하고 다음 조건 계속. 속도에 따른 조기 중단이나 불리한 반복의 대체 없음. 저장 검사가 전체 실행 안전성을 깨뜨리면 중단하고 이유 기록 |
| 반복과 예열 | 조건·엔진마다 사전 실행 1회로 총 48회. 정식 통계에서 제외하고 원자료 보존. 별도 프로세스이므로 측정 JVM의 JIT 예열로 취급하지 않는다. |

초기 load는 각 엔진·크기마다 공식 클라이언트 1스레드와 `dataintegrity=true`로 수행한다. 키·모든 필드·바이트를 정규화한 전체 해시가 양쪽에서 같은지 확인한다. 정상 종료한 baseline을 정식 실행마다 별도 DB 파일로 복제한다. 측정은 `dataintegrity=false`로 실제 갱신값을 생성한다. 매 실행은 새 JVM이다. 매 실행의 직전 audit가 실제 측정 DB 파일의 전체 행을 읽는다. 따라서 cold file cache 조건이 아니다. 파일 시스템 cache를 비우거나 온도를 통제하지 않으며 측정 JVM의 JIT는 예열하지 않는다.

### 저장 검사 합격 조건

모든 실행은 종료 후 연결을 새로 열어 전체 행을 읽는다. 합격 조건은 재개방 성공, 유일한 TEXT 키, 행마다 10개 필드, 필드마다 100바이트, 최종 행 수가 초기 행 수에 성공 INSERT 수를 더한 값과 일치하는 것이다. C는 전후 전체 해시가 같아야 한다. 성공 UPDATE가 있는 A·B·F는 최종 baseline 필드 중 적어도 하나가 달라야 한다. D·E에서 성공 INSERT가 있으면 전체 해시가 달라야 한다. 불일치는 성능 비교에서 실패로 분류한다.

이 검사는 실제 저장 변경과 형식을 확인한다. 같은 필드를 여러 번 갱신한 순서나 모든 동시 갱신의 최종 바이트가 정확하다는 증명은 아니다. 정확한 최종값·부분 갱신·binary 왕복은 별도의 결정적 연결 시험으로 검증한다. 공식 반환 상태와 바인딩의 처리 행·바이트도 함께 대조한다.

공식 워크로드의 read와 scan은 존재하는 acknowledged 키에서 시작한다. 삭제가 없고 scan 길이가 최소 1이므로 성공 read·scan마다 최소 1행을 반환해야 한다. 반환 행 합계의 하한은 성공 read 수와 scan 수의 합이며, 상한은 read 수와 scan 수의 100배를 더한 값이다. 반환 필드 바이트 합계는 반환 행 수의 1,000배와 같아야 한다.

## 분석 방법

| 가설 | 지표 | 방법 | 채택 기준 |
|---|---|---|---|
| H1 | 완료 수·non-OK·재개방 검사 | 전수 확인. 확률 표본 추론이나 신뢰구간 해당 없음 | 정식 240회 모두 1,000논리 연산, non-OK 0건, 저장 검사 충족 |
| H2 | E의 대응 처리량 비율 | 조건별 n=5, 대응 비율 중앙값. seed 226으로 10,000회 복원추출한 percentile 95% 구간 | 구간 상한 <0.8이면 채택, 하한 ≥0.8이면 기각, 나머지 보류 |

방법은 [SciPy bootstrap 문서](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.bootstrap.html)의 percentile 정의를 따른다. 계산은 Python 표준 라이브러리로 재현한다. 작은 n의 bootstrap 구간은 정밀한 모집단 보장을 주지 않는다.

| 항목 | 규칙 |
|---|---|
| 제외 기준 | 사전 실행·load·검증·profile은 정식 처리량 통계에서 제외. 정식 실행은 삭제하지 않는다. |
| 실패한 실행 | timeout·비정상 종료·non-OK·연산 부족·audit 실패를 실패로 셈. 실패한 쌍이 있는 조건은 비교 가능 false. 성공분 통계가 있더라도 그 조건의 승자 판정 금지 |
| 다중 비교 | 보정하지 않는다. H2의 4조건은 탐색적 개별 판정이며 전체 워크로드·DB 일반 우위를 추론하지 않는다. |

공식 stdout·stderr·properties·명령·시각·실행 순서·exit·timeout·환경·재시도·전후 저장 검사를 원자료에 보존한다. 집계는 원자료만 읽고 결정적으로 다시 생성한다. 원자료 해시는 수집 뒤 고정한다. 표에서는 처리량과 지연을 소수 첫째 자리, 비율과 구간을 소수 셋째 자리까지 쓴다. 원자료의 정밀도는 보존한다. 처리량만으로 끝내지 않고 p50·p95·p99, 실제 연산 혼합, 실패 수와 모든 반복 범위를 함께 공개한다.

## 추가 분석

- 측정과 분리한 양쪽 실행에서 CPU·wall time·macOS sample을 관측해 바인딩·JVM·엔진 비용을 구분한다.
- 처리 바이트와 native 호출 수를 논리 연산 수와 대조한다. F의 read/update 호출 증가를 구분한다.

## 위험 요소와 대응

| 위험 요소 | 대응 |
|---|---|
| 다른 프로세스와 열·OS cache가 순서를 교란 | 양쪽 교대 실행과 load average·시각 기록. 다른 프로젝트 프로세스를 종료하지 않는다. |
