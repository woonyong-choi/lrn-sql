# YCSB 동등 조건 측정: 실험 결과

## 요약

고정한 자동 commit 설정에서 ToteDB의 E 범위 조회 처리량은 SQLite보다 낮다. 1만 행·worker 1의 중앙값은 각각 59.4 ops/s와 4,048.6 ops/s이며, 대응 비율은 0.015 [95% 구간 0.013, 0.016]이다. 양쪽 5회씩 측정한 값이다. H1은 정식 240회 모두 통과했고, H2는 사전 지정한 E의 네 조건에서 모두 채택한다.

이 결과로 DB 전체의 승자를 정할 수는 없다. SQLite WAL·준비 문장 캐시를 튜닝하지 않은 설정 비교이며, 작은 합성 부하와 새 JVM의 비용을 포함한다. 엔진 최적화와 공개 API 변경은 하지 않았다. 연결 도구와 반복 가능한 측정 기록을 추가했다.

| DB | ToteDB 0.1.0, macOS 시스템 SQLite 3.51.0. 2026-10-18 확인 |
| 머신 | Apple M4, 10코어, 24GiB, macOS 26.5.2 arm64 |
| 입력 | 합성 데이터. 1천·1만 행, TEXT 키, 10필드×100바이트 BLOB |
| 조건 | 공식 A~F, worker 1·4, 조건·엔진당 5회, 매회 논리 연산 1,000개 |
| 저장 설정 | 자동 commit. 페이지 8,192바이트, 연결당 cache 256페이지. SQLite DELETE/FULL, fullfsync OFF, mmap OFF |
| 표본 | 계획·실제 정식 240회, 사전 실행 48회 |

YCSB core와 A~F는 수정하지 않았다. [공식 릴리스](https://github.com/brianfrankcooper/YCSB/releases/tag/0.17.0)의 파일과 JAR를 SHA-256으로 고정했다. 양쪽은 같은 Java SQL·JNI 바인딩을 사용하며, 엔진별 공개 API 아래 비용은 포함했다. SQLite의 결과를 ToteDB wire 형식으로 다시 인코딩하지 않았다. 명령과 계약은 [바인딩 안내](../../../bench/ycsb/README.md)에 있다.

공식 처리량의 시간은 worker 시작부터 join까지로 연결 초기화·종료를 포함한다. 지연은 DB 메서드별 histogram이다. 외부 wall time은 JVM 시작까지 포함하며 원자료에서 구분했다. 각 반복 전 실제 DB 전체를 audit로 읽었으므로 cold cache 실험이 아니다. 측정 JVM의 JIT 예열은 하지 않았다.

### 실제 작업과 저장 검사

| 엔진 | 논리 연산 | native 시도 | BUSY 재시도 | 반환 행 | 반환 필드 바이트 | non-OK |
|---|---|---|---|---|---|---|
| totedb | 120,000 | 136,786 | 6,729 | 1,033,295 | 1,033,295,000 | 0 |
| sqlite | 120,000 | 132,737 | 2,726 | 1,030,336 | 1,030,336,000 | 0 |

위 표는 정식 실행 합계다. native 시도에는 F의 추가 update와 BUSY 재시도가 포함된다. 양쪽 모두 재시도 예산 소진은 0건이었다. 모든 성공 read·scan의 반환 행 하한·상한과 반환 바이트를 대조했다. 반환 필드 바이트는 반환 행 수의 1,000배였다. 오류를 빠른 처리량으로 잘못 세지 않았다.

두 엔진의 초기 전체 해시는 크기마다 같았다. 매 실행 후 별도 JVM으로 다시 열어 키 유일성·순서, 필드 수·길이, 최종 행 수와 성공 INSERT 수를 대조했다. C의 전후 해시는 같았고, A·B·F는 실제 필드 변경을 확인했다. D·E는 성공 INSERT 수와 추가 행이 일치했다. 누락 행은 없었다. 동시 무작위 갱신의 모든 최종 바이트를 증명하는 검사는 아니다. 정확한 값·부분 갱신·binary·scan 순서는 별도의 결정적 연결 시험으로 검증했다.

## 추가 분석

1만 행·worker 1, C와 E, 양쪽 엔진에 같은 1,000논리 연산을 별도로 실행했다. [profile 원자료](profile/data/raw/20261018T003900Z-be5fb10-profile/manifest.json)와 [집계](profile/results/summary.json)를 보존했다. 사전·분석 실행 모두 오류와 저장 불일치는 없었다. profile의 반복 수는 1이므로 성능 순위를 추론하지 않았다. 실제 시작 시각은 manifest의 `2026-10-18T00:34:53.236165+00:00`이다. run_id의 시각 부분은 수동으로 붙인 식별자이며 실제 시작 시각은 아니다.

E의 [ToteDB sample](profile/data/raw/20261018T003900Z-be5fb10-profile/trials/10000-E-t1-measured-1-totedb/sample.txt)에는 `Native_execute → tote_exec → exec_query → select_run → scan_rows` 호출과 `merge_sort`, `select_ctx_free`, 할당·해제, `pread`가 관측됐다. [범위 조회 소스](../../../src/sql/database_select.c)의 전체 순회·행 보관·정렬 경로와 일치했다. 측정한 E의 제한 요인은 TEXT 색인으로 범위를 바로 순회하지 못하는 경로라고 해석한다. 스택 표본 수를 실행 시간의 정확한 비율로 바꾸지는 않았다.

E의 [SQLite sample](profile/data/raw/20261018T003900Z-be5fb10-profile/trials/10000-E-t1-measured-1-sqlite/sample.txt)에는 `sqlite3_step`, B-tree 이동과 페이지 읽기, insert commit의 `fsync`가 관측됐다. JVM·JNI 비용도 포함됐다. C는 ToteDB sample에 실제 DB 호출 스택이 없었고 SQLite는 sample 파일을 얻지 못했다. C와 다른 짧은 조건의 병목은 이 프로파일로 확정하지 않는다. 실제 CPU 시간·RSS·fault는 각 `process.json`에 있으며 정식 통계와 합치지 않았다.

## 해석

E의 차이는 TEXT 범위 조회의 전체 행 순회·정렬 비용과 일치한다. 제품 성능을 바꾸는 작업은 하지 않았으므로 이 결과를 최적화 성과로 설명하지 않는다. E는 별도 최적화 후보가 되지만, 다음 변경은 색인 경로를 적용한 뒤 같은 조건에서 다시 측정해야 한다.

A·F의 일부 조건에서는 ToteDB 처리량이 높고, 읽기 중심 B·C와 E에서는 낮았다. 비교 범위는 자동 commit의 저장 방식과 준비 문장 재사용 여부를 포함한 현재 호출 경로다. 작은 실행의 초기화·JIT·운영체제 잡음과 넓은 범위 때문에 전체 DB의 일반 우위나 배포 선택으로 확대하지 않는다. 설계 기본값은 바꾸지 않았고, [빌드와 시험](../../build-and-test.md)에 공식 YCSB 재현 경로를 추가했다.

|---|---|
| 다른 프로세스와 열·OS cache가 순서를 교란 | 다른 프로젝트 작업을 종료하지 않았다. 부하 평균을 trial마다 기록했고 양쪽 순서를 교대했다. 온도와 OS cache를 통제하지 않았다. |
| 1,000연산의 짧은 실행과 JVM 비용이 DB 비용을 가림 | 새 JVM과 초기화 포함 runtime을 명시했다. 별도 profile을 정식 결과에서 제외했다. 짧은 조건의 병목은 확정하지 않는다. |
| 성공 반환만으로 실제 저장·결과 소비를 입증 부족 | 공식 반환 상태, native 호출 수·반환 바이트, 매회 전후 전체 audit를 대조했다. 결정적 연결 시험도 따로 실행했다. |
| 독립 난수열과 D/E의 요청 혼합 차이 | 초기 해시가 같았고 실제 연산 수를 남겼다. 같은 요청 순서라고 표현하지 않는다. |
| TEXT 범위 조회의 정렬·메모리 비용 | E를 구분해 보고하고 실제 sample을 보존했다. 정식 timeout은 없었다. |
| 동기화 옵션 이름이 실제 내구성 동등성을 뜻하지 않는 설정 | 정상 자동 commit 동기화 의도를 맞췄다. 전원 장애에서의 내구성 동등성은 확인하지 않았다. |
| 작은 표본과 여러 조건으로 우연한 차이를 과대해석 | 각 조건 n=5, 전체 범위와 대응 구간을 공개했다. 보정 없는 탐색적 개별 판정이다. |

## 한계

- SQLite는 이 머신의 시스템 빌드다. compile options는 manifest에 있다. WAL, 준비 문장 캐시, batch를 튜닝한 최상 성능 비교가 아니다. 도입할 DB의 승자는 판정 불가다.
- 합성 데이터와 작은 로컬 embedded 경로다. ToteDB의 실제 outbox·ACK 큐 end-to-end 처리량이나 다중 프로세스 성능을 재지 않았다.
- 연결당 명목상 cache 크기는 같지만 실제 메모리 비용과 페이지 종류는 다르다. 전원 장애·하드웨어 오류·장시간 안정성을 증명하지 않는다.
- YCSB의 요청 난수는 고정하지 못했다. 같은 분포와 초기 상태이며 동일 연산열 비교는 아니다. 짧은 JVM과 제어하지 않은 머신 부하의 영향을 포함한다.

## 재현 방법

저장소 루트에서 실행한다. Java 21, Python 3.9 이상, C 컴파일러와 SQLite 개발 헤더가 필요하다. 최초 build에는 고정 JAR 다운로드를 위한 네트워크가 필요하다.

```sh
python3 bench/ycsb/run.py build
python3 bench/ycsb/run.py test --output build/ycsb/recheck
RUN_ID=20261018T002649Z-be5fb10-check ./docs/experiments/ycsb-sqlite/run.sh verify
RUN_ID=20261018T002649Z-be5fb10-check ./docs/experiments/ycsb-sqlite/run.sh analyze
```

같은 검사 로그 id가 이미 있으면 새 `-check` 접미사를 사용한다. 원자료 해시와 파일 목록을 검사하고 집계를 다시 만든다. 재분석 결과의 세 파일은 수집 직후 결과와 바이트까지 같았다. 기존 수집 폴더는 덮어쓰지 않는다. 다시 실측하려면 다른 출력 폴더를 지정한다.

```sh
python3 bench/ycsb/run.py collect --output build/ycsb/recollection --run-id recollection
python3 bench/ycsb/run.py verify --output build/ycsb/recollection
```

별도 profile 원자료도 같은 분석기로 검사한다. 다시 profile을 수집할 때는 새 출력 폴더를 지정한다.

```sh
python3 bench/ycsb/run.py verify --output docs/experiments/ycsb-sqlite/profile
python3 bench/ycsb/run.py profile --output build/ycsb/reprofile --run-id reprofile \
  --sizes 10000 --workloads C,E --threads 1 --repetitions 1 --operations 1000 --timeout 180
```

기록된 최초 profile은 `RUN_ID=20261018T003900Z-be5fb10-profile ./docs/experiments/ycsb-sqlite/run.sh profile`로 실행했다. 해당 명령은 기존 원자료가 있으면 덮어쓰기를 거절한다.

연결 코드의 독립 검증은 수집 소스 `be5fb10`의 깨끗한 별도 worktree에서 수행했다. 문서 폴더를 cwd로 CLI 전체를 실행했고 단위 시험 14개, 양쪽 JNI 시험, 공식 Client 축소 실행 48개가 통과했다. 전후 audit와 native 호출 수를 직접 대조했으며 두 차례 재분석 결과가 같았다. [검증 판정](validation/independent-verification.json)과 [검증 원자료 압축 파일](validation/independent-checks.tar.gz), [해시](validation/SHA256SUMS)를 보존했다. 이 축소 실행을 정식 성능 표본에 넣지 않았다.

```sh
mkdir -p build/ycsb/saved-validation
tar -xzf docs/experiments/ycsb-sqlite/validation/independent-checks.tar.gz -C build/ycsb/saved-validation
python3 bench/ycsb/run.py verify --output build/ycsb/saved-validation/checks
```

수집 소스의 [Linux CI](https://github.com/woonyong-choi/totedb/actions/runs/39082700683)는 YCSB·sanitizer·SQL 대조·workflow 검사를 통과했다. [패키지 검사](https://github.com/woonyong-choi/totedb/actions/runs/39082700687)도 통과했다. PR에서 실행하지 않는 게시 job은 건너뛰었다. 이 CI는 macOS 성능 숫자의 재측정이나 전원 장애 검증이 아니다.
