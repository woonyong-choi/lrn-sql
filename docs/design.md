# 설계 노트 — 무엇을 고르고 무엇을 버렸나

이 문서는 lrn-sql 이 왜 지금의 자료구조를 쓰는지, 검토했다가 버린 대안은
무엇이고 왜 버렸는지, 그리고 지금 남아 있는 한계가 무엇인지를 적는다.
숫자는 전부 저장소 안의 명령으로 다시 낼 수 있는 것만 인용한다.

## 0. 제약

- 외부 라이브러리 없음. C11 표준 라이브러리와 POSIX pthread 만 쓴다.
- 데이터는 **파일 하나**에 고정 크기 페이지로 들어간다. 페이지 크기는
  `sysconf(_SC_PAGESIZE)` (Linux x86 4KB, Apple Silicon 16KB).
- 실행 단위는 **문장 하나**다. `BEGIN`/`COMMIT` 이 없고 autocommit 만 있다.
- 목표 규모는 100만 행. 10만 행까지는 어떤 선택을 해도 멀쩡해 보인다는 것을
  이 저장소가 직접 겪었다 (§4).

## 1. 행 저장 — 슬롯 페이지 힙

페이지 앞에서 슬롯 디렉터리가 자라고 뒤에서 행 데이터가 자란다. 삭제는
슬롯을 `FREE` 로 바꾸고 free-slot 체인에 매다는 톰스톤 방식이다.
→ [`src/storage/table.c`](../src/storage/table.c)

행의 주소는 `row_ref_t = {page_id, slot_id}` 이고, B+Tree 리프가 이 값을
들고 있다.

### 버린 대안 ① — 슬롯 디렉터리 없이 행을 페이지에 밀집 배열

행 크기가 고정(`row_size`)이므로 `page + i * row_size` 로 바로 찾을 수 있다.
슬롯 8바이트가 행마다 없어지니 밀도도 좋다.

버린 이유: **삭제가 행을 움직인다.** 구멍을 메우려면 뒤 행을 당겨야 하고,
당기는 순간 `row_ref_t` 가 가리키던 위치가 전부 틀어진다. B+Tree 리프가
그 주소를 들고 있으므로 행 하나를 지울 때마다 인덱스 엔트리를 줄줄이
고쳐야 한다. 구멍을 안 메우면 "이 칸이 살아 있나"를 알 방법이 없다.
슬롯 디렉터리는 **행의 물리 위치와 인덱스가 보는 주소 사이의 간접 한 겹**을
사기 위해 8바이트를 내는 거래다.

### 버린 대안 ② — 인덱스 구성 테이블 (B+Tree 리프에 행 자체를 저장)

점 조회가 리프 한 번으로 끝난다. 힙을 따로 읽지 않으니 `id = ?` 경로에서
페이지 접근이 한 번 줄고, id 순 범위 조회는 리프 순회만으로 완결된다.

버린 이유: **리프가 분할될 때 행이 이동한다.** 지금은 secondary index 가
없어서 티가 안 나지만, 붙이는 순간 secondary index 는 "행이 어디 있는지"를
가리켜야 하고 그 위치는 리프 분할마다 바뀐다. 해법(InnoDB 처럼 secondary
index 가 기본키를 들고 다니게 하기)은 있지만, 그러면 secondary 조회가
항상 기본키 인덱스를 한 번 더 타야 한다. 힙 + 안정적인 `row_ref_t` 는
**아직 오지 않은 secondary index 를 위해 지금 치르는 비용**이다.

## 2. 인덱스 — 온디스크 B+Tree

`id(uint64) → row_ref_t`. 분할·형제 재분배·병합·루트 축소를 모두 구현했다.
리프는 `next/prev_leaf_page_id` 로 이중 연결되어 범위 스캔을 받는다.
→ [`src/storage/bptree.c`](../src/storage/bptree.c)

### 버린 대안 ① — 해시 인덱스

`id = ?` 만 보면 해시가 이긴다. O(1) 이고 트리 하강이 없다.

버린 이유: **범위 질의가 원리적으로 불가능하다.** 해시는 키의 순서를
버리는 자료구조다. 그런데 이 엔진에서 실제로 아픈 질의가 바로 범위였다.
`bench/scaling.md` 의 두 번째 표를 보면, 힙 스캔 경로는 행 수가 2배가 될
때 시간이 1.5~2.3배가 되고(테이블 크기에 비례), B+Tree 리프 순회는
1.0~1.05배로 거의 움직이지 않는다(반환 행 수에만 비례). 해시를 골랐다면
이 표의 오른쪽 줄이 없다.

### 버린 대안 ② — 정렬 배열 + 이진 탐색

조회는 B+Tree 보다 빠르고 구현이 훨씬 짧다.

버린 이유: **삽입이 O(N) 이동이다.** 목표 워크로드가 id 오름차순 append
100만 건인데, 가운데 삽입이 아니어도 배열을 페이지 경계 너머로 늘리는
순간 재배치가 생긴다. §4 에서 보듯 이 저장소는 삽입 경로가 초선형이 되는
것만으로 이미 한 번 무너졌다.

## 3. 동시성 — 래치와 락을 나눈 두 층

| 층 | 무엇을 지키나 | 수명 | 구현 |
|---|---|---|---|
| **래치**(page rwlock) | 페이지 **바이트 배열**의 물리적 일관성 | 연산 하나 (µs) | `pager_get_page_rlatch/wlatch` |
| **락**(S/X, range) | 행과 범위의 **논리적** 일관성 | 문장 하나 | `src/server/lock_table.c` |

트리 하강은 latch coupling 이다. 자식 래치를 먼저 잡고 부모를 놓는다.
삽입·삭제는 쓰기 래치를 스택에 쌓되, 자식이 "안전"(분할·병합이 일어나지
않음)하면 조상 래치를 즉시 놓는다. 범위 스캔은 **다음 리프 rlatch 를 먼저
잡고 현재 리프를 놓는** leaf-chain coupling 이다
([`bptree.c` 범위 스캔](../src/storage/bptree.c)).

### 버린 대안 — 전역 mutex 하나

DB 전체를 뮤텍스 하나로 감싸면 위 두 층이 전부 없어진다. 정확하고, 짧고,
이 규모에서 성능도 아마 나쁘지 않다.

버린 이유: 그러면 **이 저장소를 만든 이유가 없어진다.** "DB 안에서 무슨
일이 일어나는가"를 보려고 만든 엔진에서 동시성 제어는 건너뛸 대목이
아니라 봐야 할 대목이다. 대신 이 선택의 대가는 정직하게 적어 둔다 —
래치 순서를 한 군데만 어겨도 데드락이 나고, 그래서 `header_lock → page
wlatch` 단방향 규약을 코드 주석으로 못 박고 있다
([`table.c` `alloc_heap_page`](../src/storage/table.c)).

## 4. 규모를 키웠을 때 무너진 곳

10,000행에서는 멀쩡했다. 1,000,000행으로 올리자 INSERT 가 무너졌다.

원인을 눈으로 못 찾아 **실행 중인 프로세스에 gdb 를 붙여 스택을 샘플링**했고
4회 중 4회가 `find_heap_page` 의 힙 체인 순회 위에 있었다. 결함은 두 개였다.

1. 꼬리 페이지가 찰 때마다(약 90행마다) **삭제가 한 번도 없었는데도** 빈 슬롯
   재활용을 위해 힙 체인 전체를 처음부터 걸었다 → 페이지 수 P 에 대해 O(P²).
   `heap_may_have_free_slots` 힌트로 DELETE 가 없으면 탐색 자체를 건너뛴다.
2. 서버 경로(`db.c`)는 문장 종료 시 락을 풀지만 **REPL 경로(`main.c`)만
   `lock_release_all()` 을 빠뜨려** X-lock 엔트리가 락 테이블에 영구 누적됐다.
   같은 autocommit 의미론을 두 경로에 따로 구현해 둔 탓이라, 성능 문제로
   위장한 정확성 버그였다.

### 증거는 배수가 아니라 기울기로 남긴다

"×215 빨라졌다"는 한 기계·한 번의 실행에서만 참인 숫자다. 같은 스크립트를
다른 기계에서 돌리면 ×57 도, ×107 도 나온다. 절대 배수는 캐시 크기와 메모리
대역폭을 따라 흔들린다.

반면 **N 이 2배가 될 때 시간이 몇 배가 되는가**는 알고리즘의 성질이라
기계가 바뀌어도 남는다. `python3 bench/scaling.py` 가 그 계수를 잰다
(수정 커밋 `e640fdd` 직전 코드를 `git archive` 로 되살려 같은 컴파일러로
빌드한다). 4에 가까우면 제곱, 2에 가까우면 선형이다.

| 행 수 | 개선 전 배가 계수 | 개선 후 배가 계수 |
|---:|---:|---:|
| 50k → 100k | 3.76x | 2.01x |
| 100k → 200k | 4.21x | 1.98x |
| 200k → 400k | 4.40x | 2.00x |

전체 표와 Range 질의 결과는 [`bench/scaling.md`](../bench/scaling.md),
그래프는 [`docs/scaling.svg`](scaling.svg). 둘 다 `make bench` 가 다시 만든다.

## 5. 정확성을 어떻게 믿는가

B+Tree 는 오름차순 삽입만으로는 검증되지 않는다. 그 모양은 리프가 오른쪽
으로만 쪼개지는 한 가지 경우일 뿐이고, 형제 재분배와 병합이 섞이는 삭제
경로를 밟지 못한다.

[`tests/test_bptree_property.c`](../tests/test_bptree_property.c) 는 고정
시드 난수로 삽입·삭제·혼합을 돌리고, 체크포인트마다 **트리 전체를 걸어**
불변식 8가지를 본다: 리프 깊이 일치, 노드 내 키 순증가, 부모 separator 구간
준수, 최소 점유율, 리프 체인의 prev/next 대칭과 전역 오름차순, 페이지 중복
없음, `parent_page_id` 정합, 참조 모델과의 키 집합 일치. 범위 스캔은 경계
포함/제외 4조합과 한쪽 열린 구간을 무작위로 뽑아 모델 필터와 대조한다.

이 테스트가 껍데기가 아닌지는 결함을 일부러 심어 확인했다.

| 심은 결함 | 잡아낸 불변식 |
|---|---|
| 리프를 1/2 이 아니라 1/3 지점에서 분할 | 최소 점유율 |
| 승격할 separator 키를 1 크게 | 부모 separator 구간 |
| 리프 체인의 `next` 를 일부 끊음 | 체인 방문 리프 수·키 수 |
| 언더플로우 판정을 0 으로(복구 비활성화) | 최소 점유율 |
| 범위 스캔의 하한 제외 처리 생략 | `lo == hi, 하한 제외` 경계 케이스 |

**다섯 개 모두 서로 다른 불변식에 걸렸다.**

### 이 테스트가 닿지 못하는 곳

리프 하나에 키가 4KB 페이지에서 291개, 16KB 페이지에서 1,168개 들어간다.
내부 노드 분할을 보려면 리프가 `max_internal_keys + 1` = 341개(4KB) 필요하고,
그러면 키가 약 10만 개(4KB) / 160만 개(16KB) 있어야 한다. 테스트는 리프
30개 규모로 돌기 때문에 **트리 높이가 2를 넘지 않는다.** 즉
`fix_internal_underflow_latched` 의 내부 노드 병합·재분배 경로는 여전히
`bptree_height() == 1` 로 줄어드는 루트 축소를 통해서만 간접 검증된다.
페이지 크기를 주입 가능하게 만들면 닫을 수 있는 구멍이고, 지금은 열려 있다.

## 6. 알려진 한계와 다음 병목

| 한계 | 지금 상태 | 왜 아직 없나 |
|---|---|---|
| **WAL / crash recovery** | 없음. dirty 페이지는 캐시 축출과 정상 종료 때만 디스크로 간다. 비정상 종료 시 파일이 깨질 수 있다. | 문장 단위 autocommit 만 있어서 되돌릴 단위 자체가 없다. WAL 을 넣으면 트랜잭션 경계부터 정의해야 한다. |
| **secondary index** | 없음. 인덱스는 자동 생성 `id` 하나뿐. | 지금 planner 는 규칙 기반이라 후보가 둘 이상이면 고를 근거가 없다. secondary index 는 선택도 기반 비용 모델과 같이 와야 한다. |
| **다중 테이블·JOIN** | 없음. 헤더에 컬럼 정의가 하나뿐이다. | 카탈로그 페이지가 필요하고, 이는 파일 포맷 변경이다. |
| **PostgreSQL SQL 문법** | 단일 테이블의 제한된 부분집합만 실행한다. 지원하지 않는 잔여 절은 실행 전에 거절한다. 문자열 안의 작은따옴표는 `''`로 쓴다. | 전체 호환에는 카탈로그, 식, 타입, 제약, 트랜잭션과 차등 검증이 필요하다. |
| **내부 노드 분할 검증** | property test 가 닿지 못한다 (§5). | 페이지 크기가 `sysconf` 고정이라 테스트에서 줄일 수 없다. |
| **PostgreSQL 대비 수치** | 같은 조건의 비교가 아니다. | WAL·MVCC·네트워크 프로토콜이 없다. [`docs/benchmark-postgres.md`](benchmark-postgres.md) 의 "불공정 요소" 절에 전부 적어 두었다. |

**다음에 무너질 곳**은 DB 파일이 OS 페이지 캐시를 벗어나는 지점이다.
1M 행이 약 52MB 이므로 지금 측정은 전부 캐시 안에서 일어난다. 그 선을
넘으면 버퍼 풀 프레임 256개(4KB 기준 1MB, 16KB 기준 4MB)가 실제 병목이
되고, LRU 정책과 dirty watermark 가 처음으로 의미를 갖는다. 그때 재야 할
것은 ops/sec 가 아니라 **캐시 미스율과 실제 디스크 I/O 횟수**다
(`.debug` 가 이미 쿼리별 `page_loads`·`cache_misses` 를 찍는다).

## 7. PostgreSQL 18 부분집합 호환 목표

이 저장소는 자체 저장 엔진을 유지하면서 [PostgreSQL 18 SQL 명령 목록](https://www.postgresql.org/docs/18/sql-commands.html)과 [SQL 문법](https://www.postgresql.org/docs/18/sql-syntax.html)을 비교 기준으로 삼는다. 당장의 목표는 현재 구현한 단일 테이블 SQL 부분집합을 같은 문법과 결과로 사용할 수 있게 만드는 것이다. 나머지 명령은 의존 기능을 설계·구현할 때 범위를 넓힌다. PostgreSQL 서버로 전달한 결과를 자체 엔진의 호환 구현으로 계산하지 않는다.

호환 판정은 문법 승인만으로 끝나지 않는다. 현재 차등 검사는 같은 스키마와 입력의 성공·실패와 결과 행을 비교한다. 타입, 스키마 변경, 트랜잭션 효과와 재시작 뒤 상태는 후속 검사 범위다. `ORDER BY`가 없는 SELECT의 행 순서는 비교 조건에서 제외한다. 미지원 문법은 데이터를 변경하기 전에 오류를 반환한다. 차등 검사의 현재 범위와 미검증 항목은 [호환성 검사](sql/pg-compatibility.md)에 기록한다.

| 기능군 | 현재 코드 | 첫 작업 |
|---|---|---|
| 어휘·리터럴·입력 종료 | 한 줄·한 문장 파서. 잔여 절은 거절하지만 일부 숫자 값은 잘못 해석된다. | [#2](https://github.com/woonyong-choi/lrn-sql/issues/2), [#4](https://github.com/woonyong-choi/lrn-sql/issues/4) |
| 테이블·스키마·제약 | 파일당 테이블 하나, 자동 `id`, `INT`·`BIGINT`·`VARCHAR` 일부. 명시적 제약 없음. | [#6](https://github.com/woonyong-choi/lrn-sql/issues/6) |
| 조회·식 | `SELECT *`, `COUNT(*)`, 단일 비교식, `ORDER BY`, `LIMIT` 일부. JOIN·NULL·일반 식 없음. | [#7](https://github.com/woonyong-choi/lrn-sql/issues/7) |
| 데이터 변경 | 단일 행 `INSERT`, `UPDATE`, `DELETE` 일부. 컬럼 목록·`RETURNING`·`ON CONFLICT` 없음. | 호환성 표를 세분화한 뒤 후속 이슈 생성 |
| 트랜잭션·복구 | 문장별 실행. `BEGIN`·`COMMIT`·`ROLLBACK`과 WAL 없음. | [#8](https://github.com/woonyong-choi/lrn-sql/issues/8), [#9](https://github.com/woonyong-choi/lrn-sql/issues/9) |
| 서버·관리 명령 | 자체 HTTP API. 권한·역할·확장·복제·PostgreSQL 세션 명령 없음. | 명령별 의존성을 확인한 뒤 후속 이슈 생성 |

작업 순서는 잘못된 성공을 막는 입력 검증, PostgreSQL 18 차등 검사, 스키마·타입 기반 확장, 질의와 변경, 트랜잭션·복구, 관리 명령이다. 저장 파일 형식이 바뀌는 작업은 기존 파일의 열기·전환·복구 규칙을 먼저 정한다. 검증한 부분집합만 호환으로 표시하고, 명령 목록 전체를 지원하는 것으로 표시하지 않는다.
