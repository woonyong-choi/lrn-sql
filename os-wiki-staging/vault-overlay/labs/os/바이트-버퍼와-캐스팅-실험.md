# 바이트 버퍼와 캐스팅 실험

## 작은 질문

- GDB에서 같은 주소를 `x/s`, `x/16xb`, `x/gx`로 보면 왜 서로 다르게 보일까?
- “주소를 캐스팅해서 구조체로 본다”는 말은, 정확히 어느 바이트를 어떤 규칙으로 해석한다는 뜻일까?
- OS 디버깅에서 “이 포인터는 유저 포인터인가 커널 포인터인가”를 왜 집요하게 구분해야 할까?

## 왜 필요한가

운영체제 디버깅의 대부분은 “바이트를 올바른 타입으로 해석하는 문제”다.

- 크래시 덤프에서 스택/레지스터/구조체를 해석할 때
- 시스템 콜 인자가 “유저가 준 주소”인지 확인할 때
- 페이지 테이블 엔트리(PTE)처럼 비트 필드를 읽을 때
- 장치 버퍼(디스크, 네트워크, 터미널)가 준 바이트를 파싱할 때

이 실험의 목표는 다음 한 문장을 몸으로 이해하는 것이다.

> 메모리는 바이트 배열이고, 타입은 바이트를 해석하는 규칙이다.

## 핵심 모델

### 1) 같은 바이트의 “모습”은 해석 규칙에 따라 바뀐다

같은 바이트라도 다음처럼 “보는 방법”이 다르면 전혀 다른 의미가 된다.

- raw bytes: 그냥 16진수 나열 (`x/16xb`)
- integer: 엔디안 규칙으로 정수 해석 (`x/wx`, `x/gx`)
- pointer: “다른 바이트를 가리키는 값”으로 해석 (`p/x ptr`)
- string: `\\0`까지 ASCII로 해석 (`x/s`)
- struct field: 레이아웃(오프셋/패딩) 규칙으로 해석 (`p *(struct T *)addr`)

### 2) 엔디안(little-endian)은 “정수 해석”의 기본 규칙이다

x86-64에서 메모리의 바이트 순서를 정수로 읽으면 little-endian이다.

## 예시 상황: 같은 8바이트를 4가지로 읽기

다음 8바이트가 메모리에 있다고 하자.

```text
48 65 6c 6c 6f 00 00 00
```

- 문자열(`x/s`)로 보면: `"Hello"`
- 64비트 정수(`x/gx`)로 보면(little-endian):
  - `0x0000006f6c6c6548`
- 바이트 배열(`x/8xb`)로 보면:
  - `bytes[0]=0x48`, `bytes[1]=0x65`, ...
- 32비트 정수(`x/wx`)로 보면:
  - 하위 4바이트 `0x6c6c6548` (문자 4개가 뒤집혀 보이는 이유가 엔디안이다)

## 예시 상황: 구조체는 “바이트 + 레이아웃 규칙”이다

```c
struct foo {
  uint8_t  a;   // 1 byte
  uint32_t b;   // 4 bytes (정렬 때문에 보통 4바이트 경계)
};
```

이 구조체는 대개 다음처럼 배치된다(패딩 포함).

```text
offset 0: a (1B)
offset 1-3: padding (3B)
offset 4-7: b (4B)
```

즉, `addr`에서 `a`를 읽는 것과 `b`를 읽는 것은 “같은 바이트 배열에서 서로 다른 오프셋”을 읽는 일이다.

## Linux / Windows에서는

현실 OS도 원리는 같다. 다만 더 강하게 “유저 메모리 vs 커널 메모리”를 분리하고, 잘못된 접근을 막기 위한 장치가 많다.

- Linux: 유저 포인터는 직접 역참조하지 않고 `copy_from_user()` 같은 경로로 안전하게 복사한다(개념적으로).
- Windows: 유저/커널 경계와 예외 처리 모델을 통해 잘못된 접근을 다룬다(개념적으로).

## PintOS

PintOS에서는 같은 원리를 “교육용으로 단순화된 형태”로 자주 마주친다.

### 실험 A: syscall 인자로 들어온 버퍼를 여러 방식으로 본다

1) `write(fd, buf, size)` 같은 syscall에서 `buf`는 “유저 가상주소(VA)”다.
2) 커널은 그 주소의 바이트를 문자열로 볼 수도 있고, 정수로 볼 수도 있고, raw bytes로 볼 수도 있다.

코드로는 보통 다음 흐름을 타게 된다(경로는 구현에 따라 다를 수 있다).

- `pintos/userprog/syscall.c`: `syscall_handler()`가 `struct intr_frame *f`에서 인자를 읽는다.
  - 예: `f->R.rsi`가 `buf` 역할을 하는 레지스터 인자일 수 있다(ABI는 과제 구현을 따른다).

GDB에서 확인 포인트(아이디어):

```gdb
b syscall_handler
c
p/x f->R.rsi
x/16xb f->R.rsi
x/s   f->R.rsi
x/gx  f->R.rsi
```

### 실험 B: “스택 포인터로 struct thread를 찾는다”는 뜻을 바이트로 확인한다

PintOS는 보통 “현재 커널 스택 포인터를 페이지 경계로 내림”해서 `struct thread *`를 얻는다.

- `pintos/threads/thread.c`: `running_thread()` 매크로가 `pg_round_down(rrsp())` 같은 방식으로 현재 스레드를 찾는다.
- `pintos/include/threads/thread.h`: `struct thread`가 “4KB 페이지의 아래쪽”에 있고 커널 스택이 위에서 아래로 자란다는 모델을 설명한다.

이때 중요한 관찰 포인트는 “주소 하나를 어떤 타입으로 보느냐”다.

```gdb
b thread_current
c
p/x $rsp
p/x running_thread()
p *(struct thread *)running_thread()
```

## QEMU

QEMU는 guest(PintOS)가 보는 메모리를 host(QEMU 프로세스) 메모리로 backing한다.

이 말은 다음을 뜻한다.

- guest VA/PA는 “PintOS 관점의 주소”다.
- host의 실제 포인터 주소(맥/리눅스 프로세스 주소공간)와는 다르다.
- 하지만 GDB는 QEMU의 gdbstub을 통해 “guest 메모리 바이트”를 읽을 수 있다.

## Differences

| 관점 | 같은 바이트의 의미 |
|---|---|
| C 타입 | “바이트 해석 규칙” |
| CPU instruction | “바이트를 명령어로 decode” |
| page table | “PFN + permission bit 같은 비트필드” |
| string | “`\\0`까지 읽는 규칙” |
| QEMU | “guest 메모리 바이트를 host가 관리” |

## Code Evidence

PintOS에서 좋은 실험 대상:

### syscall 인자/유저 포인터

- `pintos/userprog/syscall.c`: `syscall_handler()`에서 인자 레지스터/스택을 읽고 유저 포인터를 다룬다.

### “현재 스레드 찾기”와 구조체 캐스팅

- `pintos/threads/thread.c`: `running_thread()`/`thread_current()`는 스택 포인터를 페이지 기준으로 내림하여 `struct thread`를 찾는다.
- `pintos/include/threads/thread.h`: 같은 페이지 안에서 `struct thread`와 커널 스택이 공존한다는 모델을 설명한다.

## Numeric Example

페이지 오프셋 계산은 “주소를 바이트로 자르는 기본 연산”이다.

```text
address = 0x8048123
offset  = address & 0xfff
        = 0x123
page    = address & ~0xfff
        = 0x8048000
```

## Memory View

GDB 명령 예:

```gdb
x/16xb 0x8048123   # raw bytes
x/s    0x8048123   # C string
x/wx   0x8048123   # 32-bit little-endian
x/gx   0x8048123   # 64-bit little-endian
p/x    (uint64_t)0x8048123
p      *(struct thread *)0x8048000
```

## Debug Checklist

- 이 주소는 virtual인가 physical인가?
- 이 주소는 user인가 kernel인가?
- 이 바이트를 어떤 타입으로 보고 있는가?
- endian을 고려했는가?
- struct alignment와 padding을 고려했는가?
- pointer 값과 pointer가 가리키는 내용을 구분했는가?
